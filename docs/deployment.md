# Deployment examples and network prerequisites

These manifests are environment-specific examples from a thesis prototype, **not** a turnkey installation. The thesis used an on-premises K3s control plane with Verda instances joining the same cluster over a WireGuard tunnel. Review all site names, node selectors, IP ranges, credentials, image versions, GPU capacity and cloud-spend limits before applying anything. No commands in this document have been run against a cluster as part of this documentation update.

## Choose one provider environment

- `manifests/provider/aalto/` is the Aalto K3s example. Its provider Deployment is pinned to `control01.k3s.aalto.fi`, uses host networking and privileged WireGuard access, mounts `verda-provider-config`, and reads **`verda-secrets`** in `kube-system` with keys `client-id`, `client-secret`, and `k8s-token`. The endpoint and SSH key IDs in its ConfigMap are site-specific; check them before deployment. Do not commit a populated Secret or join token. The startup script sent to Verda includes the K3s join token and a newly generated WireGuard private key; restrict access to uploaded scripts, check Verda's retention/access controls, and plan credential rotation. Code attempts to delete the uploaded script after instance creation, not after successful bootstrap; do not assume it is immediately inaccessible.
- `manifests/provider/minikube/` is a development example, **not** the thesis evaluation cluster. It refers to image `ca-verda:dev` with `imagePullPolicy: Never` and Secret **`verda-credentials`** with keys `client-id` and `client-secret`. Its ConfigMap, network and cluster-join settings require further local adaptation; do not assume the Aalto `k8s-token` arrangement applies here.
- `config.yaml` at the repository root is a separate local example. Neither provider Deployment mounts it. The two provider ConfigMaps contain different node-group sets, location lists, prices and network settings. In `settings.py`, a node group with multiple `locations` expands into one group per location. Configured `hourly_price` is not a verified live price.

The provider's gRPC Service is `verda-cloud-provider.kube-system.svc.cluster.local:8086`; `manifests/autoscaler/cluster-autoscaler-cm.yaml` points the external-gRPC client there. The autoscaler files also include RBAC. `manifests/autoscaler/cluster-autoscaler-service.yaml` contains a **ServiceMonitor** requiring the Prometheus Operator CRD: omit or split that file in clusters without it (the Service and ServiceMonitor currently share a file). Do not apply both provider directories or indiscriminately apply `manifests/provider/`—the parent is not itself a deployment choice. The README on the base branch still shows a broad `kubectl apply -f manifests/provider/` example; do **not** follow it. A separate README PR replaces that recipe.

For review before an Aalto deployment, compare the individual files under `manifests/provider/aalto/`, `manifests/autoscaler/` and `manifests/routemanager/` with your cluster. For Minikube, examine `manifests/provider/minikube/` instead. `scripts/dev-deploy.sh` still references the provider **parent** directory and mutates Minikube networking and certificates; it is not a validated deployment recipe in its current form.

## Network and bootstrap checks

1. Select a **single** WireGuard gateway host and adapt the provider's `hostNetwork`, privileges, `/dev/net/tun` and `/lib/modules` access to it. The packaged `src/verda_cloud_provider/templates/verda_init_k3s.sh.j2` is chosen by `script_template: k3s` at runtime; it currently installs `v1.35.3+k3s1` and includes a hard-coded Aalto hostname mapping. More importantly, its `[Peer]` stanza has **no initial gateway `Endpoint`**, so a fresh cloud node cannot be assumed to initiate a tunnel handshake. Resolve and test gateway reachability and fresh-node bootstrap before using this as a deployment recipe. The duplicate top-level `templates/verda_init_k3s.sh.j2` still installs `v1.32.3+k3s1` but is not chosen by default. Align the **packaged** template with your control-plane version and DNS/network before attempting scale-out. The thesis evaluated `v1.32.3+k3s1`; this does not validate the current `v1.35.3+k3s1` image/template combination.
2. Ensure K3s joins via the tunnel (`wg0`) and advertises the tunnel address as the node IP, with Flannel on `wg0`. The thesis configured on-premises Flannel VXLAN's Pod MTU to **1370** (1500 Ethernet minus WireGuard to 1420, then VXLAN overhead); Aalto deployed `/etc/rancher/k3s/flannel-conf.json` through Ansible **before** K3s startup. That site configuration is not supplied here. Verify your own CNI, Pod/Service CIDRs and routing rather than assuming these exact values.
3. The Aalto ConfigMap and thesis use cloud tunnel network `10.200.0.0/24` and gateway `10.164.4.101`. Local nodes need a route to the tunnel network via that gateway. `manifests/routemanager/daemonset.yaml` is an **Aalto-specific** privileged route installer; it excludes `control01.k3s.aalto.fi` and nodes labeled `node.kubernetes.io/role=cloud-worker`. This PR narrows the route it installs from `/16` to `/24`, but `ip route replace` for `/24` **does not remove a pre-existing `/16` route**. Inspect existing routes and plan any migration explicitly; this PR does not delete them. IP forwarding and NAT on the gateway are configured by `entrypoint.sh`. The Aalto ConfigMap defines `WG_NETWORK` as `/24` but the Aalto Deployment does **not** inject it, so the entrypoint defaults NAT's source prefix to `10.200.0.0/16`; its injected `WG_ADDRESS` is also `/16`. Review the actual effective `WG_NETWORK`, `WG_ADDRESS`, `POD_CIDR`, `SVC_CIDR` and egress interface before changing the network. Do not apply a route manager to a live cluster without confirming it targets the intended hosts.
4. Review the provider's WireGuard peer setup as well: `src/verda_cloud_provider/services/wg_service.py` currently contains hard-coded Minikube-era allowed networks (`10.244.0.0/16`, `10.96.0.0/12`, `192.168.49.0/24`), while the Aalto ConfigMap supplies `10.42.0.0/16` and `10.43.0.0/16`. This discrepancy must be resolved/tested before claiming an Aalto deployment is reproducible from these files. A successful Pod rollout is not evidence that a cloud worker can join or route traffic.
5. Install/configure NVIDIA GPU Operator (see `deploy/gpu-operator/values.yaml`) so the required device resources appear on cloud workers. Verify the actual advertised MIG resource name before requesting it. The thesis's single-node multi-workload experiment used a two-A100 instance with `all-1g.10gb`; this does not guarantee that a current GPU Operator configuration or any other instance type exposes the same resources.

## Autoscaler and placement

The current `manifests/autoscaler/cluster-autoscaler.yaml` uses image `v1.35.0`, `--cloud-provider=externalgrpc`, and `--cloud-config=/config/cloud-config`. It currently sets `--max-node-provision-time=15m`, `--scale-down-delay-after-add=10m` and `--scale-down-unneeded-time=60m`. The thesis's displayed deployment had image `v1.30.0`, a **60m** provisioning time and **60m** delay after add. These are historical versus current examples; this PR does **not** overwrite running-policy flags with thesis values. Match Cluster Autoscaler to the actual Kubernetes cluster version before deployment.

The thesis's cloud opt-in uses zone `topology.kubernetes.io/zone=verda` plus toleration of `node-role.kubernetes.io/cloud=true:NoSchedule`. Per-group `max_size` and the autoscaler's `--max-nodes-total` place limits on capacity, but this repository does not provide a general budget enforcement layer. Avoid treating a setting from one environment as a universally safe spending limit.

**Not verified here:** Kubernetes schema acceptance, secret availability, compatible software versions, gateway connectivity, GPU discovery, scale-out/scale-in or actual cloud costs. Those require an explicitly authorized and configured test cluster.
